   - Установка — через Helm по `docs/quickstart/quickstart.md`. Не забудьте настроить доступ к веб-интерфейсу и хранение данных (это отдельно оговорено в ТЗ).

## 1. Архитектура (её надо уметь объяснить на защите)

```
Runtime Radar ──(API или выгрузка JSON)──> [adapter: normalize()] ──> внутренняя модель
                                                                       │
                     ┌─────────────────────────────────────────────────┤
                     ▼                    ▼                             ▼
              Дерево процессов        Таймлайн                  Сетевой граф
                     └──── общий выбор (selectedExecId) связывает все три вида ────┘
```

Ключевые решения и почему:
- **Слой-адаптер `normalize()`.** Сырые события Runtime Radar переводятся во внутреннюю модель **в одном месте**. Если формат окажется не таким, как ждали, правится один файл, а не весь UI.
- **Два режима загрузки данных: файл JSON и live API.** Основной режим — загрузка файла: демо работает без кластера, а если Runtime Radar упадёт на площадке, вы не останетесь с пустым экраном. Live API — бонус.
- **Процесс идентифицируется по `exec_id`, а не по PID.** PID переиспользуются системой, и по ним дерево склеится неправильно. В Tetragon (на нём построен Runtime Radar) у каждого процесса есть уникальный `exec_id` и `parent_exec_id`. **[проверить]**, что API Runtime Radar отдаёт эти же поля.
- **Общее состояние выбора.** Клик по процессу в любом виде подсвечивает его в дереве, его события на таймлайне и его соединения в сетевом графе. Именно это и есть «единый интерфейс» из ТЗ.

**Стек (рекомендация):** React + TypeScript + Vite.
- Дерево и сетевой граф — **Cytoscape.js** (для дерева — раскладка `dagre`). Одна библиотека на два вида.
- Таймлайн — **ECharts** (или vis-timeline).
- Тесты — **Vitest** + **React Testing Library** (unit), **Playwright** (e2e).

Все эти библиотеки open-source с разрешающими лицензиями. Правило «не использовать чужую интеллектуальную собственность без согласия» не нарушается: лицензия и есть согласие. Перечислите их в документации.

## 2. Данные: откуда брать события

1. В веб-интерфейсе Runtime Radar: Runtime → Parameters → включить sources, добавить **Allow filter** на namespace `hackathon`, сохранение **All** → Apply (ТЗ, шаг 2).
2. Создать активность (ТЗ, шаг 3), например:
   ```bash
   kubectl create namespace hackathon
   kubectl -n hackathon run demo --image=alpine -- sleep 3600
   kubectl -n hackathon exec demo -- ls /
   kubectl -n hackathon exec demo -- cat /etc/os-release
   kubectl -n hackathon exec demo -- sh -c "sleep 1; ls /tmp; wget -qO- http://example.com > /dev/null"
   # повторить несколько раз с паузами — нужен материал для таймлайна
   ```
3. Проверить: Runtime → Events, тестовый контейнер на месте, события видны.
4. **Выгрузить события в JSON.** Как именно — смотрите в `docs/guides/help/help.md` и в сервисах `public-api` / `history-api` репозитория **[проверить]**.
   - Запасной вариант — сырые события Tetragon. Найдите под Tetragon (`kubectl get pods -A | grep -i tetragon`) и сохраните его вывод в файл (`kubectl logs ... > events.jsonl`). Точные namespace, имя контейнера и метки зависят от установки — **[проверить]**.
5. **Сетевые соединения** — это не события `process_exec` / `process_exit`. Это отдельные события (в Tetragon — kprobe на `tcp_connect` и подобные). Убедитесь, что соответствующий source в Runtime Radar включён, иначе сетевой граф будет пустым **[проверить]**.

Сохраните 2–3 реальные выгрузки в `fixtures/` — на них будут строиться тесты и демо.

## 4. Проверки, слой 1 — тесты логики (самое ценное)

Самое хрупкое место — превращение событий в дерево и таймлайн. Тестируем внутреннюю модель после `normalize()`.

Обязательные случаи:
- Родитель → потомок связываются по `exec_id` / `parent_exec_id`.
- **Переиспользованный PID:** два процесса с одинаковым PID и разными `exec_id` — это два разных узла.
- **Сирота:** родитель запустился до начала мониторинга → процесс становится корнем, а не теряется.
- **Порядок:** `exit` пришёл раньше `exec` → всё равно один узел, с корректными началом и концом.
- **Дубликаты** событий не создают дубликаты узлов.
- **Живой процесс:** `exec` без `exit` → узел без времени окончания, UI это показывает.
- **Цикл** в ссылках на родителя (битые данные) → обход завершается, без бесконечной рекурсии.
- **Несколько контейнеров** в одной выгрузке → фильтр разделяет их корректно.
- Пустой ввод, битый JSON, наносекунды во временных метках.
- **Нагрузка:** 10 000 событий обрабатываются быстро (например, < 500 мс), UI не виснет.
- **Эталонный снимок:** реальная выгрузка из `fixtures/` → результат сравнивается со снапшотом.

Пример (Vitest). Названия полей — как в Tetragon; подправьте под реальный формат Runtime Radar:

```ts
// src/model/processTree.test.ts
import { describe, it, expect } from 'vitest';
import { buildProcessTree } from './processTree';

const exec = (id: string, parent: string | null, binary: string, t: string, pid = 100) =>
  ({ type: 'exec', execId: id, parentExecId: parent, pid, binary, args: '', time: t });
const exit = (id: string, t: string) => ({ type: 'exit', execId: id, time: t });

describe('buildProcessTree', () => {
  it('связывает родителя и потомка по execId', () => {
    const t = buildProcessTree([
      exec('a', null, '/bin/sh', '2026-01-01T00:00:00Z'),
      exec('b', 'a', '/bin/ls', '2026-01-01T00:00:01Z'),
    ]);
    expect(t.roots.map(n => n.execId)).toEqual(['a']);
    expect(t.byId.get('a')!.children.map(n => n.execId)).toEqual(['b']);
  });

  it('не склеивает процессы с одинаковым PID', () => {
    const t = buildProcessTree([
      exec('a', null, '/bin/sh', '2026-01-01T00:00:00Z', 42),
      exec('b', null, '/bin/ls', '2026-01-01T00:00:05Z', 42),
    ]);
    expect(t.byId.size).toBe(2);
  });

  it('сирота становится корнем', () => {
    const t = buildProcessTree([exec('b', 'missing', '/bin/ls', '2026-01-01T00:00:01Z')]);
    expect(t.roots.map(n => n.execId)).toEqual(['b']);
  });

  it('exit раньше exec — один узел с концом', () => {
    const t = buildProcessTree([
      exit('a', '2026-01-01T00:00:03Z'),
      exec('a', null, '/bin/sleep', '2026-01-01T00:00:00Z'),
    ]);
    expect(t.byId.size).toBe(1);
    expect(t.byId.get('a')!.end).toBe('2026-01-01T00:00:03Z');
  });

  it('дубликаты не создают лишних узлов', () => {
    const e = exec('a', null, '/bin/sh', '2026-01-01T00:00:00Z');
    expect(buildProcessTree([e, e]).byId.size).toBe(1);
  });

  it('цикл в ссылках не вешает обход', () => {
    const t = buildProcessTree([
      exec('a', 'b', '/bin/sh', '2026-01-01T00:00:00Z'),
      exec('b', 'a', '/bin/sh', '2026-01-01T00:00:01Z'),
    ]);
    expect(t.byId.size).toBe(2);
    expect(t.roots.length).toBeGreaterThan(0); // цикл разорван, процессы не потерялись
  });

  it('10k событий — быстро', () => {
    const events = Array.from({ length: 10_000 }, (_, i) =>
      exec(`p${i}`, i ? `p${Math.floor(i / 2)}` : null, '/bin/sh', '2026-01-01T00:00:00Z', i));
    const t0 = performance.now();
    buildProcessTree(events);
    expect(performance.now() - t0).toBeLessThan(500);
  });
});
```

Отдельно — тесты на `normalize()` против реальной выгрузки из `fixtures/`: ни одно событие не потерялось, у каждого процесса есть `execId`.

## 6. Проверки, слой 3 — безопасность (это прямое требование ТЗ)

> ТЗ: «Для задач, связанных с безопасностью, сгенерированный ИИ код обязательно проверяется командой на уязвимости и небезопасные практики».

### XSS — главный риск этого проекта
Аргументы команд, имена бинарников, пути к файлам — **данные, которые контролирует атакующий**. Например, в контейнере выполнили `sh -c "<img src=x onerror=alert(1)>"`. Если UI вставит эту строку как HTML, атакующий выполнит JS в браузере аналитика.
- В React выводить только через `{value}`. **Никаких `dangerouslySetInnerHTML` и `innerHTML`.**
- **ECharts:** `tooltip.formatter` возвращает **HTML-строку**. Любые поля событий в нём обязательно экранировать (функция `escapeHtml`). Это самое вероятное место дыры.
- Подписи Cytoscape рисуются на canvas — они безопасны. Но HTML-тултипы и панели рядом с графом проверять так же.
- В ESLint включить правило `react/no-danger: error`.

Тест:
```tsx
// src/components/DetailsPanel.test.tsx
import { render, screen } from '@testing-library/react';
import { DetailsPanel } from './DetailsPanel';

it('не исполняет HTML из аргументов процесса', () => {
  const payload = '<img src=x onerror="window.__xss=1">';
  render(<DetailsPanel node={{ execId: 'a', binary: payload, args: payload } as any} />);
  expect(document.querySelector('img')).toBeNull();
  expect(screen.getAllByText(payload, { exact: false }).length).toBeGreaterThan(0);
  expect((window as any).__xss).toBeUndefined();
});
```
Такой же тест — на `escapeHtml` для тултипов ECharts.

### Секреты
- Репозиторий будет **публичным**. Токены и пароли к Runtime Radar не должны попасть ни в код, ни в историю git.
- Хранить их в `.env`, который добавлен в `.gitignore`. В репозиторий кладётся только `.env.example` с пустыми значениями.
- Секреты в браузерном бандле видны всем. Если нужен токен к API, ходите к API через dev-прокси Vite или маленький backend, а не напрямую из фронтенда.

### Сканеры (через Docker — так проще всего на Windows)
PowerShell, из корня проекта:

Флаги — по текущим версиям инструментов. Если какой-то не сработает, сверьтесь с `--help` **[проверить]**.

Если UI тоже упаковывается в контейнер или деплоится в k8s:

## 8. Правила работы с ИИ-помощником (Claude, ChatGPT, Copilot и т.п.)

ТЗ разрешает ИИ, но команда отвечает за результат и должна объяснить архитектуру на защите. Поэтому:

1. **Сначала факты, потом код.** Дайте ИИ реальный пример события из `fixtures/`. Не позволяйте ему придумывать названия полей.
2. **Не верить слову «готово».** Сделано только то, что прошло `npm run check`. Любое «всё работает» без запуска тестов — непроверенное утверждение.
3. **Перед принятием кода задать ИИ (и себе) вопросы:** какие граничные случаи не покрыты? Где самое вероятное место ошибки? Есть ли вывод данных события в HTML без экранирования?
4. **Каждый кусок ИИ-кода, который отображает данные событий, проверять на XSS** (раздел 6). Это требование ТЗ, а не пожелание.
5. **Маленькие шаги:** одна функция → её тест → прогон → следующая. Не генерировать весь проект за один запрос.
6. **Понимать каждое ключевое решение.** Если не можете объяснить, почему так, — спросите ИИ «почему» и проверьте ответ, пока не поймёте. Жюри спросит.
7. **Вести лог использования ИИ** (инструмент → этап → что делал). Он нужен для базового файла.
